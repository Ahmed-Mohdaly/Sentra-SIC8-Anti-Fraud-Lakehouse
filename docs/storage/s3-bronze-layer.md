## 1. فلسفة طبقة Bronze في معمارية البحيرة (Medallion Architecture)

في معمارية بحيرة البيانات الحديثة (Medallion Architecture)، تمثل طبقة **Bronze** المصب الأول لكافة البيانات الواردة من مصادرها الخام:
* **عدم قابلية التعديل (Immutability):** بمجرد كتابة ملف في S3 Bronze، لا يتم تعديل محتواه نهائياً (Append-Only).
* **الحفاظ على الحقيقة التاريخية الكاملة (Full Fidelity):** تُخزن السجلات كما وصلت تماماً دون حذف أي حقول أو إجراء عمليات تنظيف أو تصحيح، لتمكين فرق البيانات من إعادة بناء أي نموذج تحليلي أو إعادة معالجة البيانات من الصفر (Historical Replay & Backfill).
* **الفصل الصارم للبادئات (Prefix Partitioning):** يتم تقسيم البيانات في مجلدات منفصلة تعكس صنف البيانات ومصدرها الأصلي.

## 3. الفرق الجوهري بين تجزئة كافكا وتجزئة S3 (Kafka vs S3 Partitioning)

من أكثر المفاهيم التي تسبب التباساً لمهندسي البيانات الجدد هو الخلط بين "Partition كافكا" و "Partition مجلدات S3":

```text
┌──────────────────────────────┬──────────────────────────────────┬──────────────────────────────────────┐
│ وجه المقارنة                 │ تجزئة كافكا (Kafka Partitions)   │ تجزئة مجلدات S3 (S3 Prefixes)        │
├──────────────────────────────┼──────────────────────────────────┼──────────────────────────────────────┤
│ وحدة التخزين                 │ ملف متسلسل مجزأ داخل Broker     │ بادئة افتراضية في مسار الملف (Prefix)│
│ آلية التوزيع                 │ hash(user_id) % 3                │ Hive-style partitioning (year/month) │
│ الهدف الهندسي               │ توازي الاستهلاك وضمان الترتيب     │ تسريع الاستعلام وتخطي الملفات غير    │
│                              │ الزمني لكل مستخدم (FIFO)         │ المطلوبة (Partition Pruning)         │
│ التكلفة والأثر               │ عددها محدود (3 بارتشنز)          │ عددها مرن وغير محدود                 │
└──────────────────────────────┴──────────────────────────────────┴──────────────────────────────────────┘
```

* **في مسار البث اللحظي:** يقوم موصل S3 Sink بتسمية المجلدات بـ `partition=0/` و `partition=1/` ليعكس رقم بارتشن كافكا الأصلي؛ هذا يتيح إعادة تتبع أي حدث إلى موقعه الأصلي في كافكا بسهولة بالغة.
* **في مسار الاستخراج اليومي والتزايدي:** تُقسم المجلدات بأسلوب Hive-Style: `year=YYYY/month=MM/day=DD/` لتمكين محركات Spark و Databricks و AWS Athena من قراءة معاملات يوم محدد دون مسح كامل الباكت.

## 4. إعدادات الأمان والتشفير (S3 Security & Permissions)

* **التشفير الساكن (Encryption at Rest):** الباكت مشفر بالكامل بتقنية **SSE-S3** (Server-Side Encryption with Amazon S3 Managed Keys - AES-256)، مع دعم التشفير عبر **AWS KMS** للملفات الحساسة.
* **الحماية من الوصول العام (Block Public Access):** مفعل بنسبة 100% على مستوى الباكت لمنع أي تسريب للبيانات المالية التخليقية خارج شبكة المؤسسة.
* **صلاحيات الوصول (IAM Least Privilege):**
  * موصل Kafka Connect يملك فقط صلاحية `s3:PutObject` على البادئة `bronze/`.
  * مهمة الاستخراج `TransactionExtractor` تملك صلاحية `s3:PutObject` على `bronze/` و `bronze/quarantine/`.
  * مستخدمو التحليلات في Databricks يملكون فقط صلاحية `s3:GetObject` و `s3:ListBucket` دون إمكانية الحذف.

## 5. مسار العزل والبيانات التالفة: `bronze/quarantine/`

لحماية بحيرة البيانات من التلوث ببيانات غير مطابقة للمواصفات:
* عندما تقوم بوابة فحص البيانات ([`DataQualityGate`](file:///home/syd/Downloads/archive/src/ingestion/extractor.py#L135-L208)) باكتشاف سجل مفقود منه حقول إلزامية، أو يحتوي على مبلغ سالب غير منطقي، أو مكرر داخل الدفعة، يتم فصله فوراً.
* لا يتم تجاهل السجل أو حذفه في الذاكرة! بل يُحفظ في ملف مستقل تحت:  
  `bronze/quarantine/transactions/year={Y}/month={M}/day={D}/quarantine_{run_id}.jsonl`.
* يحتوي كل سطر معزول على السجل الخام الأصلي كاملاً، مضافاً إليه حقلان:
  * `rejection_reason`: سبب الرفض الدقيق (e.g. `Negative amount -500.0 on non-refund scenario`).
  * `quarantined_at`: التوقيت الزمني الدقيق لعملية العزل.
* يتيح ذلك لمهندسي البيانات تشغيل عمليات التدقيق (Audit) وإصلاح الأخطاء وإعادة معالجتها لاحقاً.
