## 1. التخزين الصفي مقابل التخزين العمودي (Row-Oriented vs Columnar)

من أهم القرارات الهندسية في بناء بحيرات البيانات هو اختيار صيغة التخزين المتوافقة مع طبيعة استهلاك البيانات:

```text
┌─────────────────────────────────┬─────────────────────────────────┐
│ التخزين الصفي (Row-Oriented)     │ التخزين العمودي (Columnar)       │
│ مثال: JSON / JSONL / CSV        │ مثال: Apache Parquet / ORC      │
├─────────────────────────────────┼─────────────────────────────────┤
│ تُخزن سجلات البيانات سطراً بسطر   │ تُخزن قيم كل عمود متجاورة معاً │
│ ممتاز لعمليات الكتابة المتسلسلة  │ ممتاز للاستعلامات التحليلية OLAP│
│ السريعة ذات الحزم الصغيرة        │ واسترجاع أعمدة محددة (Select)   │
│ تكلفة بناء الفهارس بالذاكرة صفر │ يدعم Predicate Pushdown بقوة    │
└─────────────────────────────────┴─────────────────────────────────┘
```

## 2. المقارنة التفصيلية بين الصيغتين في منصة SIC

### 2.1 صيغة `JSONL.GZ` (JSON Lines Compressed with Gzip)
* **المسارات المستخدمة:** مسار بث المعاملات اللحظي ومسار الـ CDC لكروت ومستخدمي النظام.
* **كيف تعمل؟** كل حدث مالي يُكتب كسطر JSON مستقل ينتهي بـ `\n`، وتضغط الحزمة بخوارزمية DEFLATE / Gzip.
* **لماذا تم اختيارها لمسار البث اللحظي؟**
  1. **السرعة وخفة المعالجة:** موصل كافكا يفرغ السجلات كل 50 سجلاً أو كل 5 ثوانٍ؛ بناء ملف Parquet كامل بهذه الوتيرة السريعة يتطلب إنشاء فهارس وقواميس وبيانات وصفية (Footers) تستهلك الذاكرة دون جدوى.
  2. **مرونة الهيكل (Schema-on-Read):** أحداث الـ CDC قد تتطور بإضافة أعمدة جديدة للمستخدم؛ صيغة JSONL تسمح باستيعاب أي حقول جديدة فوراً دون تعارض في كتابة الملفات الخام.
  3. **نسبة ضغط هائلة:** تقلل خوارزمية Gzip حجم ملفات JSON النصية بنسبة تتراوح بين **75% و 85%**، مما يوفر تكاليف تخزين S3 ونقل البيانات عبر الشبكة.

### 2.2 صيغة `Snappy Parquet` (Apache Parquet with Snappy Compression)
* **المسارات المستخدمة:** استخراج الجداول المرجعية (MCC والمدن) واستخراج المعاملات التزايدي في Airflow.
* **كيف تعمل؟** تُحول السجلات إلى جداول **Apache Arrow** ثم تُكتب كأعمدة مستقلة مع فهارس إحصائية (Min / Max / Null Count) لكل عمود.
* **لماذا تم اختيارها للمرجعيات والاستخراج التزايدي؟**
  1. **تقليم الأعمدة (Column Pruning):** عندما تقوم استعلامات Databricks بدمج المعاملات مع أسماء المدن فقط (`SELECT city_name FROM cities`), يقرأ المحرك فقط كتلة بيانات عمود `city_name` ويتجاهل باقي الأعمدة بالكامل، مما يقلل الـ I/O بنسبة 90%.
  2. **دفع الشروط لأسفل (Predicate Pushdown):** بفضل بيانات الـ Metadata الموجودة في ذيل ملف الـ Parquet، إذا طلب الاستعلام `WHERE mcc = 5411`، يفحص المحرك فهارس الـ Min/Max ويتخطى قراءة كتل الملفات التي لا تحتوي على هذا الكود تماماً!
  3. **سرعة فك الضغط بـ Snappy:** خوارزمية Snappy مصممة هندسياً لسرعات فك ضغط فائقة تفوق 250 ميجابايت/ثانية لكل نواة معالج، مما يسرع مهام Spark في Databricks.

## 3. معضلة الملفات الصغيرة وكيف نعالجها (The Small-Files Problem)

### 3.1 ما هي المشكلة؟
عندما يكتب موصل S3 Sink ملفاً مضغوطاً كل 50 سجلاً، ينتج عن ذلك ملفات صغيرة الحجم (تتراوح بين 5KB و 20KB). إذا تركت هذه الملفات كما هي في بحيرة البيانات وتراكمت لمئات الآلاف:
* تتدهور كفاءة استعلامات Spark لأن المحرك يقضي وقتاً في فتح وإغلاق اتصالات HTTP مع S3 يفوق وقت معالجة البيانات الفعلية!
* تزداد تكلفة استدعاءات `s3:ListBucket` و `s3:GetObject`.

### 3.2 الحل المطبق في المنظومة (The Compaction Strategy)
لحل هذه المعضلة هندسياً، تعتمد المنصة على استراتيجية من مرحلتين:
1. **في طبقة Bronze (الاستيعاب):** استخدام فترات تدوير متوازنة (`file.max.records = 50`, `flush.timeout.ms = 5000`) لتأمين التوازن بين زمن الوصول القصير والحد الأدنى لحجم الملف.
2. **في طبقة Silver (المعالجة في Databricks):**
   * تقوم دفاتر Databricks المعتمدة على **Databricks AutoLoader** (`cloudFiles`) بقراءة الملفات الصغيرة المتدفقة بسلاسة وتجميعها في الذاكرة.
   * يتم كتابة طبقة **Silver Delta Lake** بحجم ملفات قياسي (Target File Size = 128MB أو 256MB) مع تنفيذ أوامر الـ Compaction الدورية:
     ```sql
     OPTIMIZE silver_transactions ZORDER BY (user_id, created_at);
     ```
   * هذا النمط المعماري يجمع بين أفضل ما في العالمين: **سرعة استيعاب لحظية في Bronze**، و **كفاءة استعلامات تحليلية قصوى في Silver و Gold**.
