### شريحة 1: العنوان والمقدمة (Title & Introduction)
- **عنوان الشريحة:** Real-Time Fraud Detection: Scaling from Process RAM to AWS ElastiCache for Redis
- **الوقت المقترح:** 1 دقيقة
- **النقاط الرئيسية:**
  - مشكلة الـ Context في المعاملات البنكية.
  - هدف المشروع: بناء Online Feature Store مركزي بزمن استجابة أقل من 10 ميلي ثانية.
  - المعمارية: Apache Kafka (MSK), AWS ECS Fargate, Redis 7, LightGBM.
- **العنصر المرئي المقترح:** أيقونات معمارية تجمع شعارات MSK, ECS Fargate, Redis, و LightGBM مع علامة زمنية `< 10ms SLA`.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "أهلاً بيكم يا شباب. النهاردة هنشوف تجربة عملية واقعية نقلنا فيها نظام كشف الاحتيال من مجرد كود بسيط بيخزن بياناته في رامات الكونتينر، لـ Distributed Online Feature Store مبني على AWS ElastiCache for Redis، وهنشوف إزاي قدرنا نحافظ على زمن استجابة لحظي تحت 10 ميلي ثانية."

### شريحة 2: مسألة العمل ومحدودية البيانات المعزولة (The Business Problem)
- **عنوان الشريحة:** Why Amount Alone Cannot Detect Fraud
- **الوقت المقترح:** 1.5 دقيقة
- **النقاط الرئيسية:**
  - الترانزاكشن المعزولة ($50) لا تكفي للحكم.
  - الحاجة للمعلومات السلوكية: سرعة الصرف، نمط الأماكن، وسرعة السفر.
  - مفهوم "سرعة السفر المستحيلة" (Impossible Travel Speed > 800 km/h).
- **العنصر المرئي المقترح:** سيناريو مرئي لكارت اتسحب في القاهرة الساعة 12:00 واتسحب في باريس الساعة 12:15 مع علامة تحذير حمراء.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "لو وصلك Event إن في حركة سحب بـ 50 دولار، مستحيل تعرف دي سليمة ولا سرقة لو بصيت على الرقم لوحده. لكن لو عرفت إن الكارت ده اتسحب بيه في القاهرة ومن ربع ساعة كان بيتسحب بيه في باريس، كده الموديل يقدر يجزم إن ده كارت مسروق لأن سرعة الانتقال مستحيلة."

### شريحة 3: المعمارية السابقة ومشاكل الـ In-Memory State
- **عنوان الشريحة:** Baseline Architecture & The State-Loss Bottleneck
- **الوقت المقترح:** 1.5 دقيقة
- **النقاط الرئيسية:**
  - المعمارية الأصلية: Kafka Topic -> Fargate Consumer -> RAM Dictionaries -> Alerts.
  - مشكلة فقدان البيانات عند الـ Container Restart.
  - عائق الـ Horizontal Scaling واستحالة مشاركة الذاكرة بين الكونتينرات.
- **العنصر المرئي المقترح:** دياجرام لكونتينرين منفصلين كل واحد جواه RAM خاصة بيه، مع إشارة استفهام على عدم مزامنة البيانات بينهما.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "في الأول، كان السيستم شغال تمام على كونتينر واحد وحاطط البيانات في رامات بايثون. بس أول ما فكرنا نشغل أكتر من كونتينر لمواجهة ضغط المعاملات، ظهرت الكارثة: كل كونتينر معزول ومش شايف حركات الكونتينر التاني. ولو كونتينر عمل Restart، الـ State كلها بتموت."

### شريحة 4: الحل المركزي: AWS ElastiCache for Redis
- **عنوان الشريحة:** The Solution: Shared Online Feature Store
- **الوقت المقترح:** 1.5 دقيقة
- **النقاط الرئيسية:**
  - Redis كمخزن مركزي في الرام فائق السرعة (Sub-2ms Latency).
  - الفصل بين البيانات المرجعية الثابتة والحالة الديناميكية المتغيرة.
  - دعم الـ Horizontal Scalability لعدد لا نهائي من الـ Consumers.
- **العنصر المرئي المقترح:** دياجرام يوضح كلاستر ElastiCache في المنتصف وتتصل به عدة Fargate Tasks بشكل متوازي.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "الحل كان إننا نفصل الـ Compute عن الـ State. خلينا الـ Fargate Containers مهمتها المعالجة بس، ونقلنا كل الـ State لمخزن مركزي مشترك عالي الأداء هو AWS ElastiCache for Redis."

### شريحة 5: تصميم هياكل البيانات في Redis (Data Structures)
- **عنوان الشريحة:** Optimized Redis Key Patterns & Data Types
- **الوقت المقترح:** 2 دقيقة
- **النقاط الرئيسية:**
  - `profile:user` و `profile:card`: JSON Strings للبيانات المرجعية.
  - `last_tx`: String لتخزين آخر إحداثيات GPS ووقتها.
  - `tx_window`: Sorted Set (ZSET) للـ Sliding Window والتنظيف التلقائي.
  - `spend_stats`: Hash لمجاميع الصرف التراكمية وحساب الـ Variance.
  - `dedup`: String مع `SET NX` لمنع التكرار (Idempotency).
- **العنصر المرئي المقترح:** جدول يوضح Key Pattern ونوع البيانات في Redis والـ Complexity الخاصة بكل عملية.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "ما حطيناش كل حاجة Strings وخلاص! استخدمنا ZSET عشان نقدر نسأل عن حركات آخر ساعة بكفاءة O(log N) وننظف القديم بـ ZREMRANGEBYSCORE. واستخدمنا Hash عشان نحسب متوسط الصرف والـ Variance بدون ما نضطر نخزن مصفوفة تاريخية لا نهائية."

### شريحة 6: هندسة الميزات وتفادي تسريب البيانات (Feature Engineering & Zero Leakage)
- **عنوان الشريحة:** 34 Features & Strict Execution Order
- **الوقت المقترح:** 2 دقيقة
- **النقاط الرئيسية:**

- **العنصر المرئي المقترح:** مخطط تدفقي يوضح خطوات: القراءة من Redis، ثم حساب الميزات، ثم كتابة التحديث، ثم تقييم الموديل.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "نقطة خطيرة جداً: مينفعش أضيف المعاملة الحالية لمتوسط الصرف قبل ما أقيس هي شاذة ولا لأ! الكود بتاعنا بيقرا الـ State القديمة، يحسب الـ Features ويقيم الموديل، وبعد كده يحدث الإحصائيات في Redis عشان نمنع أي Data Leakage."

### شريحة 7: مسار المعالجة الكامل والـ Offset Semantics
- **عنوان الشريحة:** End-to-End Processing & At-Least-Once Delivery
- **الوقت المقترح:** 1.5 دقيقة
- **النقاط الرئيسية:**
  - استهلاك الرسالة يدويًا بدون Auto-Commit.
  - إرسال التحذير مع `flush(timeout=5.0)`.
  - الالتزام بالإزاحة (`consumer.commit`) بعد نجاح الإرسال فقط.
  - التعامل مع الـ Duplicate Alerts عند الـ Downstream Consumers.
- **العنصر المرئي المقترح:** Sequence Diagram مبسط يوضح الـ Poll، ثم المعالجة، ثم الـ Alert، وأخيراً الـ Manual Offset Commit.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "إحنا قافلين الـ Auto-Commit تماماً في Kafka. الـ Consumer مش بيعمل Commit للـ Offset إلا لما يتأكد إن التنبيه وصل للـ Broker واتعمله Flush بنجاح. لو حصل أي عطل في الشبكة، الـ Offset مش بيتحرك عشان مفيش رسالة تضيع."

### شريحة 8: البنية التحتية الفعلية على AWS (Verified AWS Setup)
- **عنوان الشريحة:** Live AWS Production Topology (eu-west-3)
- **الوقت المقترح:** 1.5 دقيقة
- **النقاط الرئيسية:**
  - Region: `eu-west-3` (Paris).

### شريحة 9: قياسات الأداء والأدلة الرقمية (Benchmark & Live Latency)
- **عنوان الشريحة:** Empirical Verification: Sub-10ms Latency SLA
- **الوقت المقترح:** 2 دقيقة
- **النقاط الرئيسية:**
  - اختبار الـ In-Memory المحلي: متوسط `0.52 ms` لكل ترانزاكشن (1,927 events/sec).
  - القياس الحي على AWS Fargate عبر CloudWatch: من `6.15 ms` إلى `8.95 ms`.
  - تأثير تشفير الـ TLS والـ Network RTT (~5ms).
  - اجتياز الـ 22 اختبار وحدة بنسبة 100%.
- **العنصر المرئي المقترح:** رسم بياني يقارن زمن الاستجابة (0.52ms local vs 7.2ms live AWS) مع خط أفقي أحمر يمثل الـ 10ms SLA.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "الأرقام هي الفيصل: في الرام المحلية، المعالجة بتاخد نص ميلي ثانية. ولما شغلناها على AWS Fargate متصلة بـ ElastiCache عبر TLS، الزمن الإجمالي كان بين 6 و 8 ميلي ثانية. الـ TLS والشبكة ضافوا شوية وقت، لكننا ما زلنا جوه حدود الـ SLA اللي هو 10 ميلي ثانية."

### شريحة 10: معالجة الأعطال والـ Cutover
- **عنوان الشريحة:** Resilience, Fallbacks & Consumer Group Hazards
- **الوقت المقترح:** 1.5 دقيقة
- **النقاط الرئيسية:**
  - الـ In-Memory Fallback عند انقطاع Redis.
  - إيقاف الـ Consumer القديم قبل تشغيل الجديد لتفادي الـ Split-State.
  - حدود Fargate Quota في الحساب (2.0 vCPUs) وتخصيص 0.25 vCPU للمهمة.
- **العنصر المرئي المقترح:** رسم توضيحي لحالة الـ Fallback مع علامة تحذير تبرز عدم المزامنة العكسية بعد العودة.
- **ملاحظات المتحدث (بالعامية المصرية):**
  > "لو الـ Redis وقع لأي سبب، الكود بيحول تلقائياً للـ Local Fallback عشان الخدمة متقفش. وكمان احترمنا الـ Quota بتاعة الحساب في Fargate وشغلنا الـ Task بـ ربع Core عشان تكفي المساحة المتبقية."
